# PR15: полный путь Cron, измерения 22 октября 2026

## Решение

**Production не развёртывать. Сбор настоящих цен не запускать.**

Повторные вычисления устранены и эквивалентность результатов проверена. Однако
удалённое сравнение не подтвердило уменьшения CPU. Достаточного запаса для
Workers Free нет. Патч остаётся экспериментальным внутри Draft PR15.

Это измерение настоящего Cloudflare Worker с искусственными входными данными,
без настоящих WB, Telegram и Workers AI вызовов. Реальных ценовых наблюдений — 0.

## Что профилировалось

Локальный CPU измерен через `process.cpuUsage` и V8 inspector, отдельно от
ожидания D1/сети. Корпус: 500 текущих уникальных реакций, 300 товаров и
валидных синтетических visual profiles; варианты с 20 и 300 кандидатами.
Результаты до и после имеют одинаковые хэши. SQL-запросы заменены готовыми
строками в памяти. Эти времена не являются CPU Cloudflare.

В V8-профиле до изменений обнаружены повторные вызовы `ownerCategory`,
`productType`, `word`, `fold`, `summariseVotes` и проверки `cachedProfiles`.
`choose` повторял разбор одного товара для разных групп, `shadowChoice`
заново форматировал одинаковое время для каждого кандидата.

Один захват production-style pprof на тестовом Worker после прогрева вернул
`NO_ACTIVE_ISOLATE`. Повторного захвата не было. Это отсутствие доступного
профиля, а не нулевой расход CPU. По функциям удалённый CPU не атрибутирован;
сведения о тяжёлых функциях основаны на локальном профиле.

### CPU локального вычисления, мс на вызов

Медианы пяти блоков по 40 вызовов. Измерения включают JIT/GC и квантование
учёта CPU Windows. Строки пересекаются: их **нельзя складывать**.

| Этап | До | После |
| --- | ---: | ---: |
| Проекция 500 текущих реакций | 6,250 | 3,525 |
| Чтение/проверка 300 готовых профилей из памяти | 2,350 | 3,125 |
| Audience context, 20 кандидатов | 9,750 | 7,025 |
| Audience context, 300 кандидатов | 13,275 | 8,600 |
| River SHADOW, 20 кандидатов | 0,400 | 0,400 |
| River SHADOW, 300 кандидатов | 7,050 | 5,075 |
| Выбор 20 кандидатов | 1,575 | 0,800 |
| Выбор 300 кандидатов | 16,400 | 10,525 |
| Общий вычислительный путь, 20 кандидатов | 11,350 | 8,200 |
| Общий вычислительный путь, 300 кандидатов | 36,325 | 24,600 |

Изменения `cachedProfiles` отсутствуют; разница его времени показывает шум
измерения, а не регрессию изменённого кода. Проверки модели, версии и текущего
изображения сохранены полностью. Объём 300 профилей не уменьшался.

Сериализация типового синтетического Telegram body (922 байта) оценена отдельно:
около 0,0023 мс/сообщение; `reactionMarkup` — примерно 0,0008–0,0015 мс.
Это многократно повторённые маленькие операции. HMAC, callback, SQL изменения
голосов, leases и сетевой repair сюда не входят. `repairReactions` проверен
существующими тестами и анализом вызовов: он запускается только на иначе
свободном тике, читает максимум две записи и ремонтирует одну. Он не входит
в измеренную успешную публикацию. Его реальный удалённый CPU отдельно не измерен.

## Узкие изменения

1. Те же 13 регулярных выражений классификации создаются один раз в isolate.
   Окно 500 голосов, категории, порядок правил и Wilson не менялись.
2. Тип одинакового собственного JSON-поля переиспользуется только внутри одного
   `summariseVotes`. Все голоса и уникальные люди/товары учитываются. Разбор JSON,
   повреждённые данные, объектные поля и getters сохраняют прежнее поведение.
3. В `choose` разбор JSON и определение групп переиспользуются внутри одного
   синхронного выбора. Нет кэша между тиками, выбранный результат не кэшируется.
4. В одном `shadowChoice` форматируется один и тот же явный `ts/timezone` один
   раз; модель, priors, признаки, сортировка и запись SHADOW не кэшируются.
5. `RUNTIME_UNAVAILABLE` сопровождается безопасной диагностикой до замены ошибки
   и до расчёта остатка D1-бюджета (его ошибка не стирает первичную причину):
   конечные категории, этап, максимум три причины, защита от циклов/getters.
   Удалена запись фрагмента исходной D1-ошибки и произвольного `error.name`.
   Нет SQL, сообщения, stack, URL, заголовков или произвольных свойств ошибки.
   `CPU_LIMIT_SIGNAL` является подсказкой, не доказательством CPU termination.
   Причину старой ночной ошибки восстановить задним числом невозможно.

Точные счётчики: для 500 голосов 6500 созданий RegExp → 0 после прогрева;
для 300 SHADOW-кандидатов 301 форматирование времени → 1;
для выбора 300 кандидатов 3002 разбора JSON → 902. SQL-чтения не использовались
как измерение CPU.

Для каждой версии заново восстановлен одинаковый корпус: 20 ready, 280
исторических товаров, 500 реакций, 300 профилей, feedback включён, River SHADOW.

## Бесплатная альтернатива и точная граница доказательства

Текущий монолитный путь **не подтвердил устойчивую работу в 10 мс**.
Это не доказательство невозможности любой бесплатной архитектуры. Повторять
мелкие оптимизации или называть локальные 8,2 мс доказательством допуска нельзя.

Наиболее предметный следующий вариант — подготовка проекций отдельных товаров
небольшими независимыми задачами, без новых WB/AI/Telegram запросов:

- `productType`, отдельные visual keys для качества и River;
- точное соответствие исходным данным товара/профиля, модели, версии изображения
  и версии алгоритмов; TTL и один MAX(last_event) недостаточны;
- свежие top-500 реакций, Wilson, запреты владельца и финальные проверки каждого
  поста сохраняются; промах проекции не разрешает игнорировать дизлайки;
- например, 20 товаров на задачу: 15 задач для первоначальных 300 товаров.
  48 задач/сутки — максимум 960 попыток, запись только при изменении.
  Это расчёт объёма, **не измеренный расход D1 и не готовый rollout**.

Полная замороженная сводка в локальном эксперименте занимает 35 508 байт и
восстанавливается за 0,235 мс, но её актуальность не доказана. Такой глобальный
кэш в runtime **не добавлен**. Проекции также пока не внедрены: их промахи
возвращают тяжёлый путь, который ещё нужно устранить/измерить на staging.

Service Binding сам по себе не доказал отдельного CPU-бюджета для дочернего
вызова. Независимые Cron ограничены пятью triggers на Free. Queues доступны на
Free (10 000 операций/сутки), но разница общего ограничения Workers CPU и
таблицы CPU consumer требует отдельного подтверждения до обещания устойчивости.
Новая очередь/Worker/платная услуга ради предположения не создавались.

Следующий шаг: отдельный проверяемый дизайн ограниченных проекций с точной
инвалидацией, замером попаданий **и промахов**, D1 и независимого CPU. Только
после успешного CPU gate можно вернуться к ранее разрешённому canary до
20 естественных WB-ответов за 24 часа. Сейчас он остаётся OFF.
