## Что переносится из пути публикации

Подготовка одного товара вычисляет исходными чистыми функциями категорию,
тип, группу, аудиторию, признаки для правил качества и признаки visual для
River. Результат сохраняется в существующей изолированной staging D1.
За один отдельный вызов разрешено не более 20 товаров; AI не вызывается.
Это проверка маленьких задач в том же тестовом Worker. Новые Workers,
Queues, D1 или расписания не создаются.

Cron читает небольшие результаты. Для попадания требуется точное равенство
сырого товара, сырого профиля, приоритета источника, модели и версии кода.
Сравнение выполняется внутри SQL, без пересылки всех сырых профилей в Worker.
Изменение цены тоже вызывает промах. Возраст по часам не заменяет проверку
исходных данных. Запись подготовленного результата использует CAS: данные,
изменившиеся во время подготовки, не принимаются.

Реакции не агрегируются в постоянном кэше. На каждом выборе читается текущее
окно последних 500 голосов с исходным порядком `last_event`. Проверка
профилей и кандидатов выполняется в одной транзакции D1. Настройки владельца,
дизлайки PR14, модель, priors, часы и правила выбора остаются текущими.
При любом промахе выполняется исходный расчёт. Если недоступны и подготовка,
и исходные свежие реакции, прототип откладывает публикацию.

Повторное обновление карточки WB делает её результат неподходящим для кэша.
Поэтому для оценки общей стоимости необходимо учитывать и отдельные задачи
повторной подготовки, а не только тёплый Cron. Схема их автоматического
запуска в production пока не добавлялась.

## Один разрешённый remote-эксперимент

Пункт 9 текущего задания запрещает deployment без отдельного согласования.
Владелец явно разрешил только этот staging-прогон: до четырёх обновлений
существующего private Worker, только его D1, без production и реальных
WB/Telegram/AI. Никакого нового ресурса создавать не разрешалось.

До запуска фиксируются SHA256 A/B, проверяется текущая конфигурация,
закрытые маршруты, отсутствие чужих изменений и staging Time Travel.
Жёсткий дополнительный бюджет эксперимента: не более 20000 D1-записей
и 500000 чтений; также остановка при account totals 75000 записей или
4000000 чтений за сутки. Неполные метрики — причина остановки.

Измерения: полный CPU P50/P95/P99 исходной и подготовленной версии,
попадание/промах кэша, первая обработка новым isolate, подготовка отдельной
порции, D1 queries/rows read/rows written и исходы вызовов. Для холодного
попадания предусмотрена версия с другим статическим buildLabel; проверяется
firstInvocation и сохранённый D1-кэш. Один холодный вызов не даёт P99.
Startup и CPU invocation следует показывать раздельно, если Cloudflare
возвращает оба показателя. Локальное wall time не заменяет Cloudflare CPU.

Проверяются точные выбранные ID, captions/кнопки/фото тестовых отправок,
голоса, учёт запретов, SHADOW decision/features/scores и отсутствие настоящих
WB/Telegram запросов. Подготовка учитывается отдельно и в общей стоимости.
Цель CPU — P99 не выше 8 мс при официальном лимите 10 мс, в том числе
для промаха и небольших задач подготовки. Если gain отсутствует либо
хвост CPU не укладывается в Free с запасом,
дальнейшие варианты не перебираются: прототип остаётся OFF. Безопасный
вариант — отдельно проверить минимальный price-only патч, сохранив рабочий
production; архитектурное разделение согласовывать только после доказательства.

После теста прекращаются вызовы, восстанавливается только staging D1 до
проверенной точки, закрытая конфигурация сверяется повторно. Запрещённая
старая CPU-оптимизация не предлагается для включения. Production, Mini App,
реакции, Vision, River SHADOW и сборщик цен не меняются.
