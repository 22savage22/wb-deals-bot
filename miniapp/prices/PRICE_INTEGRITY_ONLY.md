## Состав и исправления

Два runtime-файла: `cloudflare/native_scheduler.mjs` и `prices/runtime_quote.mjs`.
Один файл с семью целевыми тестами. В трёх старых генераторах тестовых
карточек добавлены стабильный SKU и название размера; assertions сохранены.
Дополнительно этот документ и числовой отчёт `price-integrity-check.result.json`.
Миграций, bindings, новых ресурсов, конфигурационных или UI-изменений нет.

- Ошибка WB не обновляет возраст прежней цены или `checked_at`.
  Старые наблюдения сохраняются; отдельно отмечаются попытка и отказ,
  `fallback: true`, `priceStatus: unconfirmed`.
- Для публикации требуется фактический новый details-ответ WB. HTTP403,
  timeout и ошибка JSON прекращают текущую попытку без отправки старой цены.
  После недоступности WB проверяется один кандидат, затем действует
  существующий retry через пять минут; интервал успешных постов остаётся 30 минут.
- Цена и положительный остаток принадлежат одному стабильному SKU.
  Отсутствующий/повторяющийся SKU и противоречивый остаток не подтверждают цену.
- Копейки сохраняются: `24999 / 100 = 249.99`, без округления вниз.
- Подпись «Цена из ответа WB» указывает размер. Наблюдение анонимного API
  не означает подтверждённую конечную цену конкретного покупателя.
  Условия оплаты остаются unknown; destination — контекст запроса,
  а не подтверждённый адрес/цена покупателя.

Сведения помещаются в существующие JSON-поля очереди/публикации:
цена, SKU, размер, наличие, валюта, время завершения ответа, метод/тип
источника, requested context, fallback и статус подтверждения.
Отдельная история цен не создаётся. Новые WB-эндпоинты, фоновые задачи и
вызовы не добавлены; число повторов при отказах может уменьшиться.

### CPU: достаточный запас не доказан

Источник — Workers Logs `$workers.cpuTimeMs`, фильтр точной версии.
Число SQL-чтений не используется как измерение CPU.

| Успешная публикация | CPU P50/P95/P99, мс | Полнота |
|---|---:|---|
| Main | 37 / 69 / 69 | 8 из 8, без sampling |
| Патч | 70 / 109 / 109 | **6 из 8: неполные логи** |

Цифры патча описывают только доступные шесть записей. Надёжное сравнение
всей пары и устойчивую регрессию по этим данным объявлять нельзя.
Один повтор чтения логов не восстановил отсутствующие записи; дополнительные
нагрузочные прогоны не выполнялись. Все 28 HTTP-ответов получены успешно.
CPU включает HTTP-драйвер и измеритель D1; это не нативный Cron.
Startup time при загрузке: 5 мс main, 4 мс патч; это не CPU первого поста.

Отдельно реальные production scheduled-события за 13:18–14:18 UTC:
47 доступных записей ok, P50/P95/P99 **13/86/98 мс**. Покрытие всех минут
не доказано, поэтому отсутствие ошибок во всём окне не утверждается.
При документированном лимите Workers Free 10 мс запас не подтверждён.
Дальнейшие CPU-эксперименты прекращены по указанию владельца.

## Риск задержек публикаций

Суточная локальная модель использует настоящий nativeTick, минутные вызовы,
128 иначе подходящих товаров и синтетический ответ WB. Это оценка поведения
алгоритма; она не измеряет реальную частоту ошибок Wildberries.

| Условия WB | Публикаций патча из 48 | Максимальный интервал |
|---|---:|---:|
| Все ответы успешны | 48 | 30 мин |
| Отказ на 5 минут к сроку поста | 48, со сдвигом | 35 мин |
| Отказ на 2 часа к сроку поста | 44 | 150 мин |
| Каждый десятый details-ответ — 403 | 48, со сдвигом | 35 мин |
| Весь день 403 или timeout | **0** | Пауза весь день |

При стартовой старой цене и нулевом checked_at исходная main в суточном
отказе тоже даёт 0. При недавнем checked_at исходная main успевает отправить
12 устаревших цен; патч — 0. Эти 12 ошибочных отправок нельзя считать
потерянными достоверными публикациями. При здоровом WB потерь в модели нет.
Восстановление WB возобновляет работу после существующего retry; пауза и
сдвиг слотов возможны без изменения настройки 30 минут.

**Нельзя одновременно гарантировать свежую числовую цену и непрерывные
ценовые посты при полном отказе единственного источника.** У строгого патча
нет режима публикации без цены. Такой продуктовый режим потребует отдельного
решения владельца и отдельной проверки; в этот минимальный PR он не добавлен.

## Откат и условный план выпуска

Предыдущая production-версия доступна для отката. Свежая точка Time Travel
основной D1 получена read-only и сохранена только локально в закрытом
игнорируемом каталоге. Production restore не выполнялся.
В staging выполнены и проверены возврат прежней версии и восстановление
начальной D1: 20 ready, 0 posts/deliveries. Локальное соединение закрыто.

После будущего разрешённого выпуска откат — **только переключение кода**
на заранее зафиксированную версию, если активная версия всё ещё наша.
Не перезаписывать чужой deployment. Миграций нет; старый код читает
прежние поля JSON, а дополнительные поля не требуют отката схемы.
**Не откатывать рабочую D1 назад во времени:** это может стереть подтверждения
уже отправленных Telegram-сообщений и вызвать дубли. Сохраняются delivery,
claims и uncertain-состояния. Не возвращать rejected в ready массово.
Возврат старого кода возвращает и известную ошибку fallback; это ограничение
отката, а не доказательство исправления. Time Travel — только для отдельной
аварии данных с остановкой отправок и сверкой Telegram, по отдельному разрешению.

План выпуска после снятия блокировок:

1. Зафиксировать конкретный commit этого небольшого PR и снова сравнить
   активную production-версию, main, bindings, настройки и точку восстановления.
2. Подтвердить приемлемую доступность публикаций при ошибках WB и достаточный
   CPU для Free. **Оба допуска сейчас не получены; выпуск NO-GO.**
3. Получить отдельное разрешение владельца на merge и конкретное развёртывание.
4. Выпустить только price-only изменение с прежними секретами, bindings,
   Cron, настройками качества/реакций/My Style, River SHADOW и Vision OFF.
5. Проверять первую естественную публикацию и следующую по обычному расписанию:
   SKU/размер/остаток/время фактического ответа, CPU/D1, отсутствие дублей.
   При ошибке — остановить выпуск и выполнить описанный откат кода.
